# GC 原型 B 评测报告：引用计数 + 备份计数循环回收

> 日期：2026-09-04　|　实现：`aluka_r/crates/aluka-core/src/gc_protos/refcount.rs`
> 基准：`aluka_r/crates/aluka-core/examples/gc_bench.rs`（`cargo run --release --example gc_bench`）
> 方法学：交替执行 + 轮间冷却 100ms + **min-of-5**（与原型 A 完全一致的负载与生命周期模型）
> 环境：Windows 10.0.26200 x64，rustc release（opt-level=3）

## 设计

- 每对象带 `strong` 强计数；分配即无主（strong=0），登记根或写入存活对象槽位时增计；
- 写屏障 = 增新减旧；减到 0 立即递归释放（析构确定性好）；
- 环无法被纯计数回收：周期性 `collect_cycles` 做标准 trial-delete
  （Bacon-Rajan mark-sweep：全候选备份计数 → 统一减内部引用 → 扫描定三色 → 收白）。

## 结果（min-of-5，与原型 A 同负载同生命周期模型）

| 场景 | 负载 | 耗时 | 即时释放 | 循环回收 |
|---|---|---|---|---|
| fib30_tree | 269 万次递归分配/弃置 | 311.2 ms（A 的 1.8×） | 269.25 万 | 0 |
| churn | 20 万分配，10% 存活 | **1596.6 ms（A 的 80.8×）** | 18.0 万 | 2000+ |
| cycles | 5 万个三节点环 | 385.5 ms（A 的 23.3×） | — | 13.5 万 |

## 正确性

与原型 A 共享测试矩阵（20 项全绿）：根移除即时释放、链式级联释放、**环垃圾被
备份计数回收**、外部持有的环不误收、共享子不双重释放。

## 观察

1. **计数操作是普遍税**：每个引用的写入/覆盖都要增减计数，fib30 每层调用多出
   add/remove_root 与 set_slot 的计数对——总耗时 1.8×；
2. **高频弃置场景放大最狠**：churn 场景 80× 差距——每次弃置的 dec 递归是逐对象
   函数调用，而 A 的批量清除是线性扫 free-list；
3. **循环检测成本高且需全堆扫描**：collect_cycles 每轮 O(全堆)，cycles 场景
   13.5 万环对象回收占 385ms 的大头；且为支持三色检测每对象多 `buffered`+`color`
   两个字段（对象头膨胀）；
4. **优点真实存在**：无全局暂停峰值（释放分散在每次 dec）、无记忆集/写屏障的
   分代簿记、对象死期确定（对 finalizer 语义友好）——但 JS 运行时的分配模式
   （高频小对象、瞬时树形）恰恰是它的最坏工况。

## 结论倾向

在本引擎的目标负载（JS 语义的高频小对象分配）下，原型 B 的常数开销全面落后；
除非未来出现「暂停时间敏感 + 低分配率」的运行形态，不作为主回收器候选。
