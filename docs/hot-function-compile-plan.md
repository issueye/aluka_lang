# aluka 热函数编译（JIT 雏形）实施方案

> 日期：2026-08-10 ｜ 依据：perf-report-v4（42.5x）+ 值类型化栈实验结论（纯 Go 无法 compact tagged value）
> 目标：在纯 Go 约束下实现"热点函数特化执行"，把合计差距从 **42.5x** 压向 **≤15x**
> （部分简单模式用例 ≤10x）。这是唯一能逼近 node（JIT 内联）的途径。
> 前置基线：commit 900833b；参考：docs/typed-value-stack-plan.md §9（值类型化栈回退结论）。

## 1. 纯 Go 下"JIT"的约束与可行形态

**硬约束**：运行时无法动态编译/加载 Go 代码（无 JIT 编译器、plugin 平台受限且需秒级 go build）。
所以"热函数编译"不能是 V8 式 JIT，而是**三管齐下的特化执行**：

| 形态 | 原理 | 预计单次调用 |
|------|------|--------------|
| 通用解释（现状） | switch 分派 + 递归 run() | ~157ns |
| ~~S-1 迭代化调用~~ | 已实验：+7.3% 变差，回退（见 §2） | — |
| **S-2 静态类型特化** | 编译器类型推断 → 特化指令（OpAddNum 等，免类型检查）| ~50-70ns |
| **S-3 O-6 原生化扩展** | 循环内简单函数整体 Go 直执行（跳过解释）| ~5-20ns（模式相关）|

**关键**：S-3（O-6 模式）已被 arrayMap 验证（16x→9.4x）；把它扩展到"热函数体整体直执行"
是把 propAccess/callOverhead/fib 类拉向 <10x 的唯一可行路径。

## 2. S-1 迭代化调用（消除 run() 递归，pprof cum 91% 的最大头）

**现状**：OpCall 快速路径 → `fastCallClosure` → **递归 `run()`**。每 JS 帧一层 Go 栈 +
run() 前导重取（frame/tmpl/code/监控门控）。

**方案**：run() 改为"单循环多帧"：
```
for {
    frame := v.cur(); tmpl := frame.tmpl; code := tmpl.Code
    for {
        switch op {
        case OpCall (快速路径命中):
            push 新帧到 v.frames → break 内层循环（重取 frame/tmpl/code）
        case OpReturn/OpReturnUndef:
            pop 帧 → frames 空则 return；否则 break 内层循环（回到调用者帧）
        case 其他: 原地执行
        }
    }
}
```
- 快速调用：帧直接 push，参数原地（已有 fastCallClosure 的栈上布置），不递归
- 慢路径（跨模块/async/generator/varargs/invoke）：仍递归（调用频率低）
- module：canFastCall 保证同模块，帧切换无需 module 保存/恢复
- 异常：handleThrow 沿帧链 unwrap（现状逻辑保留）

**预期**：callOverhead/methodCall/fib **1.5-2x**（单次 157→~90ns）；递归类最受益。
**工作量**：~400-600 行（run() 重构 + fastCallClosure 改造 + 返回/异常路径）。
**风险**：高——帧一致性、PC 保存/恢复、返回值传递、异常 unwrap。严格回归（fib/递归/
async/generator/闭包/方法调用/异常）。

> **⚠️ 实验结论（2026-08-10，S-1 已实现并回退）**
> 完整实现后基准对比：**整体 +7.3% 变差**（callOverhead +9.7%、fib +1.8% 无改善、
> methodCall -0.3%），已 `git checkout` 回退到 v4 基线（2656ms）。
>
> **失败原因**：`goto frameLoop` 的帧/tmpl/code 重取开销（每快速调用/返回多一次重取，
> 含监控门控）完全抵消了递归消除的收益。Go 函数递归本身开销极小（无栈切换硬件代价），
> 迭代化的理论收益被高估；且慢路径（async/generator/跨模块）仍递归，收益面有限。
>
> **结论**：S-1 方向关闭，不做第二次尝试。迭代化消除的是"Go 递归"而非"JS 调用语义
> 开销"（帧分配、值检查、分派），后者才是 pprof 大头。**跳至 S-2（类型特化）**。

## 3. S-2 静态类型特化（编译器 → 特化指令）

**现状**：OpAdd 每次运行时 isBigInt + String 检查（pprof binAdd 12-19%）。

**方案**：编译器做**简单类型推断**（来源分析：数字字面量/数字局部槽/数字运算结果）：
- 新指令 `OpAddNum`/`OpSubNum`/`OpMulNum`/`OpDivNum`/`OpModNum`/`OpNegNum`、
  `OpCmpNum`（数字比较）、`OpPushInt2` 等——**免 isBigInt/String/类型分派**
- VM 特化指令直接 float64 运算（pop/push 同现有，但零类型检查）
- 推断失败（来源未知/混合）→ 保留通用指令
- 序列化：新 opcode 追加（opcodes.go OpEnd 前）+ FormatVersion +1

**预期**：算术/比较/循环类（fib、s+=i、propAccess 加法部分）**1.5-2x**。
**工作量**：~500-800 行（编译器推断 + 特化指令 + VM case + 序列化）。
**风险**：中——推断保守（只对确定数字），错误推断导致错误结果（需差分）。

## 4. S-3 O-6 原生化扩展（循环内函数整体 Go 直执行）

**现状**：O-6 只覆盖数组高阶回调（map/filter/...）的单表达式（CBInstr 小栈）。

**方案**：
- **4a. 表达式覆盖扩展**：CBInstr 增加属性读链（`x.a.b`）、数字字面量运算、`Math.*`、
  字符串方法子集 → 覆盖 propAccess 的 `o.a+b+c` 模式。
- **4b. 热函数体直执行**：编译器把"循环内简单函数"（如 `function inc(){s+=i;}`、fib 尾调用）
  的**整个函数体**翻译成 Go 模板执行器（参数 → Go 计算 → 结果），完全跳过字节码解释。
  模板执行器在编译期生成（对已知模式的函数），运行期按调用计数切换。
- **4c. 简单循环直执行**：对 `for(i=0;i<N;i++) s+=o.a;` 这类循环体，检测为"可原生化"
  模式 → Go 侧循环直执行。

**预期**：propAccess/callOverhead/fib 类模式 **3-10x**（接近 Go 速度），部分 ≤10x。
**工作量**：~800-1200 行（CBInstr 扩展 + 模板执行器 + 模式识别）。
**风险**：高——模式覆盖边界（副作用/异常/this/闭包），需保守识别 + 回退。

## 5. 里程碑与验收

| 里程碑 | 内容 | 预计合计 | 状态 |
|--------|------|----------|------|
| M-H1 | S-1 迭代化调用 | ~42.5x → ~28x | ❌ 失败回退（+7.3% 变差，见 §2） |
| M-H2 | S-2 类型特化指令 | ~28x → ~20x | ⬜ 下一步 |
| M-H3 | S-3a 表达式覆盖扩展 | ~20x → ~16x | ⬜ |
| M-H4 | S-3b/3c 热函数/循环直执行 | 部分用例 ≤10x | ⬜ |

每步独立提交 + 基准门禁 + 全量测试（22 包）+ node22 差分。
实施顺序：~~S-1~~ → S-2 → S-3a → S-3b/c。

## 6. 风险与边界

| 风险 | 等级 | 缓解 |
|------|------|------|
| S-1 帧一致性回归 | 高 | 严格回归 + 差分；先跑通 fib/递归/async/异常 |
| S-2 类型推断错误 | 中 | 只对"确定数字来源"特化，其余通用；差分对比 |
| S-3 模式误识别（副作用）| 高 | 只原生化无副作用/无闭包/无 this 的纯函数；回退机制 |
| 收益不达预期 | 中 | 每步基准门禁，不达标回退 |

## 7. 结论

纯 Go 下"热函数编译"= **迭代化 + 类型特化 + 原生直执行**三件套。S-1/S-2 把解释器
推到物理下限（~50-70ns/调用），S-3 让简单模式绕过解释器到 <10x。**全部用例 ≤10x
仍不现实**（复杂模式解释器下限 ~20ns/指令 vs node JIT ~1-5ns），但合计可达 **~15-20x**，
核心交互模式（属性访问/调用/算术）显著改善。
